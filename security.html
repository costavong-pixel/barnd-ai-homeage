SEO Pro security

Customer WordPress sites do not receive our AI provider key.

Barnd AI SEO Pro separates customer installation identity from upstream AI provider credentials. The goal is to limit the blast radius of a compromised WordPress site and make cross-customer access fail closed.

Core boundary: WordPress authenticates to Barnd AI SEO API. The Barnd API authenticates to the configured AI provider. Those are different credentials and different trust boundaries.

Per-installation signing

Each hardened Pro installation can use its own Ed25519 key pair. The private signing key remains with the WordPress installation. The API stores the public identity needed to verify signed requests.

Site A private key ──signed request──▶ Barnd API ◀── public key A Site B private key ──signed request──▶ Barnd API ◀── public key B

Replay and tamper protection

Protected requests bind the site/installation identity to the HTTP method, request path, body digest, timestamp and nonce. The API rejects expired, replayed, tampered, wrong-site, inactive or revoked-key requests.

Tenant isolation

Customer-supplied resource identifiers are not sufficient authorization by themselves. Protected resource access is checked against the authenticated installation/site. Controlled migration tests verified that Sajie, Slab staging and fresh-customer installations could not use one another's identities to access resources.

Clone/copy resistance

Copying plugin files or a WordPress database is not intended to create a second authorized Pro installation. The API's site/installation binding and signing identity must still match the registered customer installation. Legitimate domain/site changes should use a controlled rebind or reactivation process.

Provider credential isolation

The upstream AI provider key is stored in protected Barnd API server configuration. It is not returned to WordPress, written into customer plugin settings, embedded in browser JavaScript or required during normal customer onboarding.

Capabilities are server-authoritative

Analysis, drafting, mutation, publishing and other consequential actions can be treated as separate capabilities. A Pro licence does not mean every action is automatically enabled. Customer defaults remain conservative; automatic publishing is not the general default.

Rate and cost controls

Central provider routing allows Barnd AI to apply per-site request limits, provider-usage controls and budget rules before an AI request is sent upstream. This also prevents one WordPress site from receiving a reusable provider credential that could bypass those controls.

Rotation and revocation

A compromised site identity can be revoked or rotated independently. That should not require distributing a new AI provider credential to every customer, because provider credentials remain behind the Barnd API boundary.

What this security model does not claim

No WordPress plugin can make a fully compromised server trustworthy. If an attacker controls the operating system or WordPress host, local secrets may be exposed. The architecture is designed to reduce cross-customer impact, block replay/tampering, keep upstream provider keys out of WordPress and make individual customer identities revocable.

Security validation status

The final SEO release inspection used sealed repository security scans, security-diff review, multi-site negative tests, runtime/source attestation, TLS/permission checks and supervisor gates. Native Deep Scan was unavailable in the final host, so the documented multi-pass Standard fallback was used rather than claiming a Deep Scan that did not run.
